# 账号、人物、属性、背包数据表与接口设计

## 1. 文档目标

本文档基于已确认需求，输出首版可落地的数据设计和接口设计，覆盖：

- 账号
- 人物
- 人物属性
- 人物背包
- 登录注册
- 人物拉取
- 属性与背包同步

目标是让后续开发可以直接据此拆本地表、云端表、Repository 和接口。

---

## 2. 设计原则

### 2.1 归属原则

首版统一按以下关系设计：

- `账号` 是登录主体
- `人物` 是养成主体
- `属性` 归人物
- `背包` 归人物

即：

- 一个账号只能绑定一个人物
- 当前账号登录后，所有首页展示、背包展示、奖励发放、穿戴结果都落到当前人物

### 2.2 落地原则

为了兼容当前项目结构，首版建议采用两层设计：

- 本地层：保留现有 `HostState`、`Inventory` 语义，但增加“当前人物上下文”
- 云端层：明确拆出 `Account`、`Character`、`CharacterAttributes`、`CharacterInventory`

这样做的好处：

- 不需要一次性推翻现有业务模型
- 首页和背包先能跑通
- 后续要接多人物时，扩展成本更低

## 3. 核心数据模型

## 3.1 Account

### 业务定义

账号是登录和鉴权的主体。

### 字段设计

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| accountId | String | 是 | 账号唯一 ID |
| accountName | String | 是 | 测试账号名 |
| loginType | String | 是 | 首版固定为 `test_account` |
| status | String | 是 | 账号状态，默认 `active` |
| boundCharacterId | String | 否 | 绑定的人物 ID |
| createdAt | Long | 是 | 创建时间 |
| updatedAt | Long | 是 | 更新时间 |

### 首版约束

- 一个账号最多绑定一个人物
- 注册成功后必须自动写入 `boundCharacterId`

---

## 3.2 Character

### 业务定义

### 字段设计

## 3.8 TaskTemplate

### 业务定义

任务模板用于定义每日任务、挑战任务和周任务的配置来源。首版虽然不接后端，但本地数据库仍需要有模板表，支持随机生成任务实例。

### 字段设计

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| taskTemplateId | String | 是 | 模板 ID |
| taskType | String | 是 | `daily / weekly / challenge` |
| taskCategory | String | 是 | `bond / vitality / focus / challenge` |
| title | String | 是 | 任务标题 |
| description | String | 是 | 任务描述 |
| actionType | String | 是 | `jump_home / jump_sign / upload_photo / take_photo / record_focus_video / upload_challenge_video` |
| targetCount | Int | 否 | 次数类目标 |
| targetDurationSec | Int | 否 | 时长类目标，专注任务使用 |
| energyCost | Int | 否 | 挑战任务启动需消耗的元气值 |
| rewardBond | Double | 否 | 亲密奖励 |
| rewardVitality | Double | 否 | 元气奖励 |
| rewardFocus | Double | 否 | 专注奖励 |
| rewardCharm | Double | 否 | 魅力奖励 |
| jumpTarget | String | 否 | 跳转目标，如 `home`、`sign_in` |
| weight | Int | 是 | 随机权重 |
| isEnabled | Boolean | 是 | 是否启用 |
| createdAt | Long | 是 | 创建时间 |
| updatedAt | Long | 是 | 更新时间 |

### 首版约束

- 每个任务类型先维护约 `10` 个模板
- 每日任务按分类随机抽取 `2~3` 个模板生成实例
- 挑战任务每天额外抽取 `1` 个模板生成实例

任务实例表示某个角色在某一天或某一周实际看到的任务记录，是任务页渲染和状态管理的直接数据源。

### 字段设计

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| taskInstanceId | String | 是 | 任务实例 ID |
| characterId | String | 是 | 人物 ID |
| taskTemplateId | String | 是 | 模板 ID |
| taskType | String | 是 | `daily / weekly / challenge` |
| taskCategory | String | 是 | `bond / vitality / focus / challenge` |
| title | String | 是 | 冗余存储标题，便于直接渲染 |
| description | String | 是 | 冗余存储描述 |
| status | String | 是 | `pending / in_progress / preview_pending / completed / failed / cancelled` |
| progressCurrent | Double | 是 | 当前进度 |
| progressTarget | Double | 是 | 目标进度 |
| rewardBond | Double | 否 | 实际奖励快照 |
| rewardVitality | Double | 否 | 实际奖励快照 |
| rewardFocus | Double | 否 | 实际奖励快照 |
| rewardCharm | Double | 否 | 实际奖励快照 |
| energyCost | Int | 否 | 挑战任务元气消耗快照 |
| startsAt | Long | 是 | 生效时间 |
| expiresAt | Long | 是 | 过期时间 |
| completedAt | Long | 否 | 完成时间 |
| failedAt | Long | 否 | 失败时间 |
| createdAt | Long | 是 | 创建时间 |
| updatedAt | Long | 是 | 更新时间 |

### 状态说明

- `cancelled`：取消或异常中断

## 3.10 TaskCompletionRecord

### 业务定义

任务完成记录用于沉淀“真实完成事实”，是周任务统计、奖励去重和本地追溯的依据。

### 字段设计

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| completionId | String | 是 | 完成记录 ID |
| taskInstanceId | String | 是 | 任务实例 ID |
| characterId | String | 是 | 人物 ID |
| taskType | String | 是 | `daily / weekly / challenge` |
| taskCategory | String | 是 | `bond / vitality / focus / challenge` |
| completionStatus | String | 是 | `confirmed / failed / cancelled` |
| rewardBondApplied | Double | 否 | 已结算亲密奖励 |
| rewardVitalityApplied | Double | 否 | 已结算元气奖励 |
| rewardFocusApplied | Double | 否 | 已结算专注奖励 |
| rewardCharmApplied | Double | 否 | 已结算魅力奖励 |
| appliedToAttributes | Boolean | 是 | 是否已写入属性 |
| countedInWeeklyStats | Boolean | 是 | 是否已计入周任务统计 |
| confirmedAt | Long | 否 | 用户最终确认完成时间 |
| createdAt | Long | 是 | 创建时间 |
| updatedAt | Long | 是 | 更新时间 |

### 首版约束

- 只有用户点击元气任务 `完成` 或专注任务 `确定` 后，才能写入 `confirmed`
- 拍照成功但未点击完成、录像结束但未点击确定，都不能写为已完成
- 周任务统计必须读取该表中的 `confirmed` 记录

## 4. 本地 SQLDelight 表设计建议

结合当前项目已有 `HostState.sq`、`Inventory.sq`，首版建议不要直接在旧表上硬改所有语义，而是新增账号和人物上下文表，再逐步迁移。

## 4.1 Account.sq

建议新增表：

```sql
CREATE TABLE Account (
  account_id TEXT NOT NULL PRIMARY KEY,
  account_name TEXT NOT NULL,
  login_type TEXT NOT NULL,
  status TEXT NOT NULL,
  bound_character_id TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

## 4.2 Session.sq

用于记录当前登录态：

```sql
CREATE TABLE Session (
  session_id TEXT NOT NULL PRIMARY KEY,
  current_account_id TEXT NOT NULL,
  current_character_id TEXT NOT NULL,
  login_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

说明：

- 当前仓库缺“当前账号/当前人物上下文”
- 这个表可以避免所有 Repository 都手传 accountId

## 4.3 Character.sq

```sql
CREATE TABLE Character (
  character_id TEXT NOT NULL PRIMARY KEY,
  account_id TEXT NOT NULL,
  nickname TEXT NOT NULL,
  avatar_url TEXT,
  default_appearance_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

## 4.4 HostState.sq 调整建议

当前已有表需要补充以下能力：

- 增加 `character_id`
- 增加 `charm`
- 保留 `mood`
- 让一条属性记录明确归属人物

建议目标结构：

```sql
CREATE TABLE HostState (
  character_id TEXT NOT NULL PRIMARY KEY,
  charm INTEGER NOT NULL,
  vitality INTEGER NOT NULL,
  mood INTEGER NOT NULL,
  bond INTEGER NOT NULL,
  focus INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

说明：

- 旧字段 `fortune` 建议废弃或迁移，不再承担首页“魅力”语义

## 4.5 Inventory 主表调整建议

当前 `Inventory.sq` 更像“背包条目表”，首版可以拆成：

- `CharacterInventory`
- `CharacterSkill`
- `CharacterItem`
- `CharacterAppearance`

如果想最小改动，也可以先保留旧 `Inventory` 条目表风格，但必须补 `character_id`。

最小改动版建议：

```sql
CREATE TABLE Inventory (
  id TEXT NOT NULL PRIMARY KEY,
  character_id TEXT NOT NULL,
  item_id TEXT NOT NULL,
  item_type TEXT NOT NULL,
  count INTEGER NOT NULL,
  data TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

其中：

- `item_type = skill | item | appearance`
- `data` 存扩展字段

说明：

- 这是过渡方案，适合快速落地
- 若要更稳定，还是建议拆子表

## 5.4 Inventory 调整

当前 `Inventory` 已包含 `userId`，建议统一改名为 `characterId`，避免混淆。

目标方向：

## 8. 任务本地接口设计建议

由于首版任务系统不接后端，任务相关接口建议先以本地 Repository 能力为准；若后续接后端，再在相同语义上补网络层。

### 8.1 每日任务读取

本地能力目标：

- 读取今日基础每日任务列表
- 读取今日挑战任务
- 读取任务详情

### 8.2 每日任务确认完成

本地处理顺序建议：

1. 校验当前任务实例状态是否允许完成
2. 写入 `TaskCompletionRecord`
3. 更新 `TaskInstance.status = completed`
4. 写入属性奖励
5. 更新周任务统计
6. 记录媒体清理结果

### 8.3 周任务进度读取

本地能力目标：

- 根据 `TaskCompletionRecord.confirmed` 数据重算周任务进度
- 返回三类任务的真实完成次数
- 返回当前抽奖券奖励档位和领取状态

### 8.4 媒体清理一致性

本地能力目标：

- 元气任务完成或重拍后，记录照片删除和系统相册删除是否成功
- 专注任务完成、失败、中断后，记录视频删除是否成功
- 即使媒体清理失败，也不得重复发放任务奖励
