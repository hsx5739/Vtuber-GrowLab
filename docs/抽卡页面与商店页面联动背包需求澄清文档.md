# 抽卡页面与商店页面联动背包需求澄清文档

## 1. 文档目的

本文档用于在“背包持久化与外观替换及抽卡预留需求”基础上，进一步澄清抽卡页面、商店页面与背包页面的联动规则。

当前代码现状已经具备一部分库存基础能力，但抽卡页和商店页仍以展示型 UI 为主，尚未完全接入统一库存。  
因此本次先输出两部分内容：

- 一组需要产品/设计/开发共同确认的关键问题
- 一份可直接继续细化与实施的联动需求草案

---

## 2. 当前现状摘要

结合现有文档与当前 UI/代码，现状可归纳为：

- 背包页已经围绕共享层 `Inventory` 建立了技能、道具、外观、碎片、票券的统一模型
- 抽卡券已存在真实库存口径，且 `lottery_ticket` 已映射到 `Inventory.items` 与 `Inventory.currencies`
- 外观“夜航校服”“晨雾便服”已进入背包定义，且具备碎片字段与图片资源映射
- 商店页当前仍使用 `shopSections` 的静态展示数据，商品只有名称、描述、价格文案，没有真实商品 ID、奖励定义、库存写入逻辑
- 抽卡页当前仍使用 `demoPools` 的展示数据，没有真实抽卡执行、扣券、发奖、重复奖励转换与背包写入逻辑
- 背包页的 UI 数据可由 `Inventory` 衍生，但商店页和抽卡页尚未共用同一套“商品/奖池 -> 奖励 -> 库存变更”链路

这意味着：

- “看得到票券”不等于“票券已被抽卡页真实消费”
- “商店里展示了抽卡券/碎片”不等于“购买后会真实写入背包”
- 当前最缺的是联动口径，而不是单纯的 UI 样式

---

## 3. 需要确认的关键问题

以下问题建议按优先级逐项回答。这 10 个问题基本决定了联动方案是否能稳定落地。

### Q1. 商店页中哪些商品需要在本期接入真实购买逻辑？

建议先明确商品范围，而不是默认全部接入。  
当前 UI 至少出现了三类商品：

- 功能道具
- 外观相关商品
- 抽卡券

待确认：

- 是否本期只接入“抽卡券 + 外观碎片”两类
- 还是将商店当前所有展示商品全部转为真实商品

### Q2. 商店统一消耗的货币是什么？

当前商店价格文案表现为“星尘”，但背包文档主线更明确的是 `Inventory` 中的道具、碎片、抽卡券。  
需要确认：

- 本期商店是否统一消耗“星尘”
- “星尘”是否已经属于真实资产，是否必须纳入 `Inventory.currencies`
- 若尚未接入真实资产，本期是否允许先做假扣减/仅演示

### Q3. 商店商品与背包资产的映射单位是什么？

需要明确每个商品购买后实际发到背包里的是什么：

- 购买“抽卡券”时，是增加 `lottery_ticket`
- 购买“夜航校服碎片”时，是增加 `skinNightSchool` 的碎片数
- 购买“晨雾便服染色券”时，是单独道具、外观碎片，还是外观变体解锁凭证

如果这一步不定，商店就只能继续停留在文案层。

### Q4. 外观相关商品的购买结果，是否允许直接解锁外观？

当前背包体系已支持两种口径：

- 外观直接解锁
- 外观碎片累计后解锁

待确认：

- 商店是否只卖碎片，不直接卖完整外观
- 是否允许某些礼包/限定商品直接发完整外观
- 若已拥有该外观，再次购买完整外观时如何处理

### Q5. 抽卡页本期要接到什么深度？

需要明确“联动背包”到底是接到展示层还是执行层：

- 方案 A：仅显示真实抽卡券数量，按钮可见但不执行真实抽卡
- 方案 B：支持真实扣券，但奖励仍用占位数据
- 方案 C：支持真实扣券、真实发奖、重复奖励转换，并同步写回背包

从落地价值看，建议至少确认到 B 或 C，避免做成只有数字联动的半成品。

### Q6. 抽卡消耗是否只允许使用抽卡券？

当前代码里抽卡券已是最明确的资产。  
需要确认：

- 单抽、十连是否都只消耗抽卡券
- 是否允许“抽卡券不足时用星尘补差价”
- 是否需要区分免费券、活动券、通用券

### Q7. 抽卡奖励池本期纳入哪些资产类型？

原始文档已经给出预留方向：技能、道具、外观都可进池。  
但这次做页面联动时，需要明确本期真实启用范围：

- 只启用外观
- 启用外观 + 道具
- 启用技能 + 道具 + 外观全量

建议不要直接默认全量，否则重复奖励、技能满级转换、池子配置维护成本会明显上升。

### Q8. 重复奖励转换规则，这次是否要真实执行？

当前已有预留规则：

- 外观重复 -> 转碎片
- 技能满级重复 -> 转道具
- 道具重复 -> 叠加

需要确认：

- 本期页面联动时，这三条规则是否都要真实生效
- 还是只先实现“外观重复转碎片”
- 若抽到未满级技能但已拥有，究竟是升星/升级/碎片化，还是仍按已有设计处理

### Q9. 商店购买和抽卡结果，是否都需要即时反映到背包页？

这决定交互链路：

- 购买/抽卡完成后是否立即刷新背包
- 是否需要在当前页显示“已获得”“已入库”“碎片 +x”
- 是否要支持从结果弹窗直接跳转到背包对应分类

建议至少做到“当前页提示 + 返回背包可见 + 数据不依赖重启”。

### Q10. 背包页对新增来源是否需要显式标记？

当资产来源变多后，用户可能无法区分是签到、任务、商店还是抽卡获得。  
需要确认：

- 是否要在背包中展示来源标记或最近获得标记
- 是否要记录 `acquireSource = shop | gacha | task | sign_in`
- 是否本期仅存 metadata，不做 UI 展示

这会影响后续埋点、日志、客服排查与结果页文案统一。

## 5. 联动需求确认版 V1

以下内容已按确认答案收敛，可直接作为后续产品、设计、开发联动的需求基线。

### 5.1 本期目标

本期目标是完成“商店/背包”的真实联动闭环，并为“抽卡/背包”保留统一资产口径：

- 商店购买能真实写入背包
- 商店获得的资产能立即在背包页查看
- 抽卡页本期不接入真实执行，但抽卡相关资产规则必须与背包统一
- 后续抽卡执行逻辑接入时，不再另起一套库存模型

### 5.2 默认范围

本期范围按以下确认结果推进：

- 商店页当前全部商品都要接入真实购买逻辑
- 商店统一使用“星尘”作为消耗货币
- 抽卡页本期不接入真实扣券和真实发奖逻辑
- 抽卡奖池配置范围先按最终目标定义完整，便于后续直接接执行层

### 5.3 商店联动规则

- 商店商品必须具备稳定商品 ID，不再只使用展示文案
- 每个商品必须绑定统一奖励定义
- 每个商品必须具备统一价格定义，价格货币固定为“星尘”
- 购买成功后，统一通过库存接口写入 `Inventory` 或统一人物状态接口
- 购买抽奖券：背包内抽奖券数量 `+1`
- 购买外观碎片：背包内对应 `skinId` 的碎片数量 `+1`
- 购买养成补给：写入人物状态系统，对应状态值 `+1`
- 购买后立即刷新背包页，确保返回背包时可看到最新结果

### 5.4 商店商品映射规则

本期商品可归为以下几类：

- 外观碎片商品：映射到对应外观碎片库存
- 抽奖券商品：映射到抽奖券库存
- 养成补给商品：映射到人物状态字段
- 其他道具商品：映射到背包内对应道具数量

约束如下：

- 外观商品本期只卖碎片，不直接售卖完整外观
- 不允许商店层自己维护一套独立库存值
- 商品文案、展示卡片、购买结果，必须能回溯到真实商品 ID 和奖励 ID

### 5.5 抽卡规则确认

虽然抽卡页本期不接入真实执行逻辑，但抽卡相关需求已确认如下，需作为后续实现约束：

- 抽卡每次消耗 10 张抽卡券
- 抽卡券属于背包统一资产
- 抽卡奖池范围包括：
- 背包内所有物品
- 技能，按“级”抽取
- 道具，按“个”抽取
- 碎片，按“个”抽取
- 星尘，单次随机奖励 5~100

### 5.6 抽卡执行层预留要求

虽然本期不做真实抽卡，但需要保证后续接入时可直接复用以下规则：

- 抽卡按钮可用状态依据抽奖券数量判断
- 执行抽卡时先扣除 10 张抽奖券
- 奖励发放统一走库存/人物状态更新链路
- 抽卡结果写入后，背包页立即刷新
- 抽卡结果中若包含星尘，应直接增加星尘余额

### 5.7 重复奖励规则

本期确认：重复奖励转换规则要真实生效，并作为后续抽卡执行的正式规则保留。

规则建议继续沿用并补齐到统一配置层：

- 外观重复：转换为对应外观碎片
- 技能重复且已满级：按技能稀有度转换为对应道具
- 道具重复：数量叠加
- 碎片重复：数量叠加
- 星尘奖励：直接累加

### 5.8 即时刷新要求

本期确认购买或抽卡后都要立即刷新背包，因此需要满足：

- 购买完成后，背包页无需重启或重新进入应用即可读到最新数据
- 商店页完成购买后，若用户返回背包，背包内容必须已经同步更新
- 后续抽卡接入后，抽卡结果确认后背包也必须立即更新

### 5.9 来源记录要求

本期确认：先不记录资产来源。

因此本期不要求：

- `acquireSource`
- 来源筛选
- 来源埋点展示 UI

但实现上建议不要阻断后续扩展，尽量避免把“来源永远不存在”写死在模型中

### 5.10 数据模型要求

本期建议补充或统一以下字段能力：

- 商店商品 ID
- 商品奖励目标 ID
- 商品奖励类型：`item | skill | skin_shard | ticket | stardust | status`
- 商品价格货币类型
- 商品价格数量
- 抽卡奖励类型与奖励数量表达
- 重复奖励标记与转换结果表达
- 星尘余额表达
- 人物状态增量写入能力

### 5.11 UI 交互要求

- 商店商品卡需要展示“可购买 / 已拥有 / 已售罄 / 条件不足”等状态
- 商店商品卡需要展示真实价格与真实购买结果
- 购买完成后，需要有明确结果反馈
- 背包刷新后，相关数量变化必须可直接看见
- 抽卡页本期允许保持展示态，但展示口径不能与最终真实规则冲突
- 背包页无需增加第二套状态管理，直接读取统一库存

### 5.12 非目标

本期默认不包含：

- 抽卡页真实执行逻辑
- 完整概率公示页重构
- 云端存档与跨端同步
- 商店限购、每日刷新、活动时段等复杂商业化规则
- 资产来源记录与展示

## 6. 推荐决策顺序

当前 10 个问题已完成确认，后续建议按以下顺序进入实施：

1. 先补齐商店商品 ID、价格、奖励映射
2. 再补齐星尘资产与人物状态写入接口
3. 然后打通商店购买 -> 背包刷新链路
4. 最后整理抽卡奖池配置与重复奖励规则，为二期抽卡执行做准备
