## Context

主角系统是一个基于Kotlin Multiplatform (KMP)的移动应用，目标是打造一个「虚拟养成 + 情感陪伴」的产品。项目已有完整的需求文档、游戏机制总纲、配置扩表规范、属性任务与抽奖细化、界面与信息架构、物料清单等6份详细文档。

当前项目处于规划阶段，需要将设计转化为可执行的开发任务。系统核心特点是：
- 配置驱动：任务、奖励、事件、卡池等通过配置表扩展，减少代码修改
- 情绪陪伴优先：避免强制验证和羞辱式文案
- 游戏化轻交互：不是强竞技游戏，而是现实反馈的轻量化表达
- 多模态支持：计时、健康数据、拍照、语音等多种任务类型
- 合规要求：抽奖概率公示、未成年人保护、隐私政策、内容安全

## Goals / Non-Goals

**Goals:**
- 构建可扩展的配置驱动架构，支持内容通过配置表扩展
- 实现完整的游戏化系统：属性、任务、事件、抽卡、皮肤、签到、技能、道具
- 提供情绪陪伴体验：AI对话、随机事件、陪伴者互动
- 支持多模态任务：计时、健康数据、拍照、语音
- 保证系统自洽：数值来源可追溯、奖励派发可审计、经济闭环
- 实现Demo最小可演示版本，验证核心循环

**Non-Goals:**
- 强竞技或排行榜系统
- 复杂的社交功能（多玩家互动）
- 3D角色模型（首版使用静态图或Live2D）
- 完整的支付系统（Demo阶段仅占位）
- 真实的灾害预警或政务通知样式
- 强制验证现实任务（采用分层奖励策略）

## Decisions

### 1. 技术架构：Kotlin Multiplatform (KMP)

**决策：** 使用KMP共享业务逻辑，Android/iOS双端独立UI

**理由：**
- 共享核心逻辑（属性计算、任务状态机、事件触发、抽卡概率）减少重复开发
- 各端可使用原生UI框架，提供最佳用户体验
- 配置表、数据模型、业务规则完全共享
- 符合移动应用跨平台开发趋势

**替代方案：**
- React Native/Flutter：跨平台UI但与原生生态集成度较低
- 纯原生开发：双端重复工作量大，维护成本高

### 2. 配置驱动架构

**决策：** 所有游戏内容通过YAML/JSON配置表管理，核心逻辑不硬编码具体内容

**理由：**
- 新增任务、事件、卡池等只需修改配置，无需改代码
- 支持热更新（如需要）
- 便于内容策划独立工作
- 保证系统扩展性和可维护性

**配置表结构：**
- `rewards/*.yaml` - 奖励包定义
- `tasks/*.yaml` - 任务定义
- `events/*.yaml` - 随机事件定义
- `gacha/pools/*.yaml` - 卡池定义
- `skins/*.yaml` - 皮肤定义
- `items/*.yaml` - 道具定义
- `skills/*.yaml` - 技能卡定义
- `buffs/*.yaml` - Buff定义
- `signin/*.yaml` - 签到规则

### 3. 统一奖励派发系统

**决策：** 所有奖励通过RewardBundle派发，使用RewardDispatcher统一处理

**理由：**
- 保证数值来源可追溯（reasonCode + traceId）
- 支持幂等性（网络重试安全）
- 便于审计和调试
- 统一处理货币、属性、物品、buff等不同类型奖励

**实现要点：**
- 每个派发操作生成唯一traceId
- reasonCode枚举：SIGN_IN, TASK_COMPLETE, TASK_VERIFY, EVENT_BRANCH, GACHA, SHOP, ITEM_USE, ADMIN, MIGRATION
- 支持批量派发和事务回滚

### 4. 任务验证策略：分层奖励

**决策：** 采用"基础奖励 + 验证加成"的分层策略，不强制验证现实任务

**理由：**
- 避免将用户当犯人，减少体验压力
- 现实任务无法百分百验真（技术限制）
- 通过奖励分档引导真实行为，而非强制验证
- 符合情绪陪伴的产品定位

**实现策略：**
- A类（自述）：点完成给少量羁绊/心境，大额奖励不给
- B/C/F/G类（可验证）：满足条件自动或手动验证，给星尘加成档
- 边际递减：同一天多次完成A类，奖励递减
- 时间门槛：某些任务要求最小时间间隔

### 5. 宿主属性系统设计

**决策：** 5个主属性（气运、能量、心境、羁绊、专注），支持buff修饰和数值夹逼

**理由：**
- 覆盖用户状态的主要维度
- 气运提供游戏化趣味，能量驱动任务，心境反映情绪，羁绊记录关系，专注面向学生
- buff系统支持果实道具和活动加成
- 数值夹逼防止溢出和异常

**实现要点：**
- 每个属性有[min, max]范围，默认0-100
- 日界/周界触发重置或衰减
- buff按加法或乘法修饰（任务奖励用乘法，展示用加法）
- 属性变化触发UI反馈和陪伴者台词

### 6. 随机事件与技能联动

**决策：** 随机事件支持技能发动，技能卡影响事件权重和选项

**理由：**
- 让抽到的技能卡有实际用途
- 增加游戏深度和策略性
- 强化陪伴者"有能力"的体感
- 避免技能卡成为纯收集品

**实现要点：**
- 技能卡分为被动、主动、演出三类
- 被动技能修改事件权重
- 主动技能在事件中提供额外选项
- 技能有冷却时间（CD）
- 事件结果通过rewardBundleId派发奖励

### 7. 数据持久化策略

**决策：** Demo阶段使用本地数据库，预留云端同步接口

**理由：**
- Demo优先验证核心循环，减少复杂度
- 本地存储足够支持单机体验
- 预留接口便于后续添加云同步
- 支持离线降级（LLM、健康数据等可选模块）

**数据模型：**
- HostState：宿主属性、buff列表、累计器
- Wallet：货币数量
- Inventory：技能卡、果实、皮肤、碎片、道具
- TaskInstance：任务实例和状态机
- EventOffer：待展示的随机事件
- SignInState：签到状态
- GachaState：卡池保底计数
- CompanionPresentation：当前皮肤和展示状态

### 8. 界面架构：5 Tab导航

**决策：** 底部导航5个Tab（主页、聊天、任务、祈愿、行囊），设置作为二级页

**理由：**
- 符合移动应用主流交互模式
- 高频功能（聊天、任务、抽卡）≤ 2步触达
- 功能有处可找，避免深埋
- Demo可裁剪为4 Tab（聊天改为FAB）

**界面映射：**
- 主页：陪伴者立绘、属性胶囊、签到入口、快捷按钮
- 聊天：AI对话、D类任务引导
- 任务：今日/周常列表、任务详情
- 祈愿：卡池、货币、抽卡动画
- 行囊：技能、道具、外观、商店、设置

### 9. AI陪伴系统设计

**决策：** 接入LLM API，提供基础陪聊和情绪陪伴，任务颁发为辅助

**理由：**
- 核心价值是情绪陪伴，AI是关键能力
- 避免过重"监工感"，任务颁发不是主要功能
- Demo可简化为固定模板任务 + 少量AI生成
- 预留离线降级策略

**实现要点：**
- System Prompt定义人设和边界
- 支持对话上下文和任务上下文
- 内容安全审核和兜底话术
- 情绪识别和共情回复

### 10. 多模态任务实现

**决策：** 计时、健康数据、拍照、语音等任务通过平台API实现，提供低配完成路径

**理由：**
- 增加任务多样性和趣味性
- 健康数据需要平台权限，需处理拒绝情况
- 拍照/语音需要权限，提供"不上传"替代路径
- 符合隐私政策和合规要求

**实现要点：**
- B类：App内计时器，支持暂停和后台
- C类：健康Kit API，未授权时显示低配完成说明
- F类：相机/相册 + 场景标签识图（不做人脸识别）
- G类：录音 + 时长检测 + 人声检测（可选ASR）
- 所有多模态任务保留A类自述路径

## Risks / Trade-offs

### 风险1：LLM API成本和稳定性

**风险：** LLM调用成本高，API不稳定影响用户体验

**缓解措施：**
- Demo阶段使用免费或低成本API
- 实现离线降级：LLM不可用时使用固定模板
- 缓存常见回复，减少API调用
- 预留自建或本地模型接口

### 风险2：健康数据权限获取困难

**风险：** 用户拒绝健康数据权限，C类任务无法验证

**缓解措施：**
- 明确说明用途和隐私保护
- 提供低配完成路径（自述）
- C类任务设为可选，不影响核心循环
- 预留假数据接口用于Demo

### 风险3：配置表复杂度管理

**风险：** 配置表数量多，引用关系复杂，容易出错

**缓解措施：**
- 建立严格的校验清单（CI/CD集成）
- 配置表带schemaVersion，支持迁移
- 提供配置表可视化工具（可选）
- 文档化引用关系和命名规范

### 风险4：抽卡合规风险

**风险：** 付费抽卡涉及法规，概率公示、未成年人保护等要求

**缓解措施：**
- 上线前完成法务评审
- 概率与配置表weight同源展示
- Demo阶段仅占位或使用虚拟币
- 预留年龄限制和消费限额接口

### 风险5：多模态验证误杀

**风险：** 拍照识图、语音检测等技术可能误杀正常用户

**缓解措施：**
- 降低验证门槛，宽容度高
- 提供申诉或重试机制
- 验证失败仍给基础奖励
- 技术选型时评估误杀率

### 权衡1：Demo范围 vs 完整体验

**权衡：** Demo阶段功能简化 vs 首版体验完整性

**选择：** Demo优先核心循环，部分功能占位

**理由：**
- 快速验证产品概念
- 降低初期开发风险
- 后续迭代可快速补充

### 权衡2：配置驱动 vs 开发效率

**权衡：** 配置表灵活性 vs 初期开发速度

**选择：** 配置驱动，初期配置表数量可控

**理由：**
- 长期扩展性和可维护性更重要
- 配置表可逐步扩充
- 减少后期重构成本
